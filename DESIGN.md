# Palot Design

## Overview

Palot should feel like a focused native workspace for long-running OpenCode tasks. The interface is quiet by default, dense where the work benefits from density, and consistent enough that people can move between tasks, settings, and workbench panes without relearning the UI.

Themes may change the visual character substantially. These rules define relationships and behavior, not one fixed palette.

## Colors

### Theme Semantics

- Components use semantic tokens such as `background`, `foreground`, `card`, `muted`, `accent`, `border`, and their sidebar equivalents. Product code should not recreate theme colors locally.
- Light and dark themes are independent. A theme only appears in a color mode it actually supports.
- Code, terminal, and diff colors may follow the app theme or use a separate registered code theme.
- Contrast strengthens or softens the relationships between surfaces, borders, controls, icons, and secondary text. It should not replace the theme's accent or semantic status colors.

## Typography

- The configured interface size drives the Tailwind type scale and shared component primitives.
- Product UI uses the named `text-sm`, `text-compact`, `text-meta`, `text-micro`, and `text-tag` roles. Compact, metadata, and micro text keep bounded offsets from the configured interface size; tag text stays tightly capped for compact badges.
- Icons that form a label with UI text use bounded semantic icon sizes. Window chrome, toolbar controls, status glyphs, and geometry-bound icons remain fixed.
- Large product headings use named responsive roles such as `text-page-title` and `text-hero`, not one-off arbitrary sizes.
- Sidebar items, group labels, captions, content, and headings derive from named theme size tokens. Avoid fixed pixel sizes in reusable navigation and settings components.
- Monospace content uses `text-code` or `text-code-compact`. Terminal, diff, and file tree sizes remain independently derived from the configured monospace size where density matters.
- Font size changes should be visible across navigation, settings, controls, content, and previews, not only on the document body.
- User-selected fonts must retain a robust platform fallback stack. Cell-grid surfaces must resolve to a monospace face.

## Layout

- App-shell surfaces fill their allocated panel with `h-full` and `min-h-0`. Viewport-sized primitives should not create extra space inside Electron's fixed root.
- Reusable surfaces respond to allocated space. Establish the query owner with Tailwind's [`@container`](https://tailwindcss.com/docs/responsive-design#container-queries) utility, name nested owners such as `@container/workbench`, and style descendants with variants such as `@sm/workbench:` or an arbitrary container breakpoint. Use viewport variants such as `sm:` only for app-shell behavior tied to the Electron window.
- Choose responsive breakpoints from child and sibling minimum sizes and interaction constraints, not device categories.
- Resizable pane separators are the visible 1px border itself. Panes meet them edge to edge; the pointer hit area comes from the resize library, not from layout gutters, and takes precedence over edge scrollbars it overlaps. A pane that stacks under a narrow container (the Pull requests list) uses a lightweight separator with the same look, an overlaid hit area, arrow/Home/End keys, and double-click to restore its default width.
- Overlay docks reserve exactly the space their content needs. Avoid decorative bottom padding that reads as an empty border or gap.
- Headers across chat, settings, and workbench panes share the same height, border ownership, and material behavior.

## Elevation & Depth

- Native window material and renderer translucency are separate controls.
- Liquid Glass uses documented native options only. Private or unstable material variants are not part of the appearance contract.
- Sidebar, content, composer, inspector, popover, and workbench opacity are derived from shared preferences instead of local alpha values.
- Reduce Transparency always wins. Every translucent surface must have a solid, readable fallback.
- Main content translucency should reveal material without making transcript text, code, inputs, or selected states hard to read.
- Prefer tonal separation, borders, and native material over heavy decorative shadows.

## Shapes

- Shared primitives own radii, borders, and control geometry. Call sites should not create a competing shape language.
- Compact navigation and controls use restrained radii. Larger surfaces may be softer when the extra containment has a real purpose.
- Pills are reserved for badges, statuses, and controls whose shape communicates their role.

## Components

### Sidebars

- The workspace has an always-visible navigation rail beside a collapsible task column. The rail is not part of the sidebar: hiding the task column leaves the rail in place, with its own edge border. The rail holds the Palot mark, one **Tasks** button for the column (a dot when anything needs you; pressing it while the column shows hides it), global destinations (Scheduled, Usage, Worktrees, Pull requests), and Settings at the bottom. Rail items are icon buttons with a tooltip and an accessible name; Tasks reports `aria-pressed`, destinations report `aria-current`. The rail is self-contained so other shells, such as Settings, can mount it; choosing Tasks from outside the workspace returns to it. The destinations own the whole content area: the task column stays hidden there without changing its remembered state, and showing navigation opens it as an overlay sheet, like a compact window.
- The column is one task list (`components/task-list`) over every enabled server. Its header is one compact row: New task (its chevron or a right-click offers a chat without a project), the search icon (task search lives only in the command palette), and one **View** menu holding Group by (Inbox, Project, Server), Working tasks, Row detail, ordering, filters, show snoozed and settled, expand or collapse, load older, Mark all as read, Settle idle tasks, and a **Projects and import** submenu (Add project folder, Import task, Manage worktrees). An active filter shows as one removable chip row under the header; nothing else.
- The footer Palot menu holds connection status, server toggles, and About. Destinations that live on the rail do not repeat there.
- **One row, one vocabulary.** Every task uses the same row, ranked by one status: needs approval, needs an answer, failed, finished unseen, working, stale (quiet for a while, or on an offline server), stopped, idle. Colour is reserved for the first four; working, stale, stopped and idle stay neutral. Ranks 1–3 form **Needs you**, always on top whatever the grouping. Idle, read rows are one line; anything with something to say gets a second line with the status sentence and only the context the grouping does not already give. A task never shows twice; chats are tasks with "Chat" where the project would be.
- **Working is docked at the bottom by default.** Running tasks get a dock under the main list's scroll, above the footer, with a top border as its structural boundary: the Working section header (label, count, and the rollup mark while collapsed) and its rows, about four rows tall and never more than a third of the body, scrolling inside itself beyond that. It is absent when nothing runs, and only Working docks: Snoozed and Settled stay at the end of the list. The bulk bar floats over the main list, above the dock. The View menu's other Working choices (under "Needs you", after the inbox, in the list) put it back in the list's flow.
- Moving a task (Move to worktree, Move to folder…) moves the task only. Before it moves, Palot checks the folder it leaves: uncommitted changes are listed with where they stay, and the action reads "Move anyway"; an unreadable status says so. A chat offers Move to project instead, and a subagent moves with its task.
- A linked pull request shows as one mark in the row's second line (state icon and number; failing checks tint it destructive, ready to merge tints it success), read from one batched query; rows without a link reserve no space. Its tooltip names the readiness verdict. A task whose composer holds something unsent (text, attachments or comments) shows a quiet pencil after its title, named "Unsent draft"; the open task does not, and typing never redraws the list. Destructive PR actions elsewhere confirm in place: the first press arms, a second press within three seconds confirms, and Escape or blur disarms.
- The Pull requests screen is master–detail: a resizable list pane (360px default, 260–640px, remembered) with debounced search, a filter menu beside Refresh (repository and organization multi-selects that accept typed names, review, checks, hide drafts) applied to every list as GitHub qualifiers, removable chips for active filters under the search field, and collapsible list groups (one gliding highlight per group, a static fill on the selected row), and a detail pane with a fixed header and subtle Summary · Timeline · Code tabs. Under a narrow container the panes stack and the detail gets a back button. The selection lives in the `pr` route param so other surfaces can deep-link to it. Holding Shift reveals per-row quick actions; every irreversible PR action confirms in place. The Code tab reuses the diff toolbar contract: a viewed checkbox starts every file row and diff header (ticking folds the file), line comments join a pending review shown on their lines and in a toolbar tray, and nothing is sent until the review is submitted.
- **The trailing slot shows exactly one thing:** the status mark for ranks 1–7, else the relative time. On hover or keyboard focus the row actions (Settle and Snooze, Stop, Wake, Move back, Unpin) overlay it with opacity only, so nothing in the row moves; they are not tab stops because the row keys reach the same actions. Everything else is the context menu, which keeps the shared task menu entries. Each triage step shows a toast with Undo when the previous state can be restored.
- **Acting from a row never happens by accident.** A permission row in Needs you shows the command and Allow once / Deny; a question row its option chips. Nothing answers without the row focused or its button pressed, a request ignores keys and clicks for 1.5 s after it appears, and focus moves to the next Needs you row after an answer. Replies go to the server that owns the request.
- The pull request screen's Guide tab (Beta) holds a review guide written on request: a rail of numbered stops beside the open stop, with ←/→ or J/K to move. Each stop shows its summary, at most one "Look closely" call, excerpts in the shared diff renderer with lettered notes on their lines, owned files, and suggested questions. Line comments on excerpts join the same pending review as the Code tab; the last stop's Finish review opens the review popover. Changed files the guide skips land in a closing Skim stop. A guide written for an older head says so and offers Rewrite.
- Hover uses one gliding highlight per group of alternatives (the rail, the task list), drawn beneath row content. Selected rows keep a static fill; keyboard focus moves the highlight to the focused row. Row actions reserve their width only while shown.
- When the task column is hidden (not in compact mode), resting on the rail's Tasks button, or on the thin edge beside the rail, peeks the list as a floating overlay. A peek never pins the column. It closes when the pointer leaves the rail and overlay, on Escape, on an outside press, and after a task is chosen. Only the pinned column owns the list's window-wide keys; the peek and the compact sheet are second views of the same data.
- Navigation sidebars share one compact menu item language: consistent height, horizontal padding, radius, icon size, typography, selected state, and focus ring.
- **The order holds.** Rows keep their order while the pointer is in the list or a row has keyboard focus, and for 3 s after the last change; then they move with a short animation (instant under reduced motion). A task that starts needing you is the exception: it rises into Needs you at once. Streaming and subagent activity never reorder rows. Scroll stays anchored to the row under the pointer or the focused row.
- Server visibility and connection management stay in the footer's Palot menu; the View menu filters by server without stopping it.
- The task menu's Copy link, after Copy task ID, writes `palot://task/<id>?profile=<id>`. Opening one from the OS shows the task on the named server, else the server that lists it, else the active one; anything not exactly that shape is ignored, never an error.
- Rows keep the shared right-click menu and the drag-out-to-new-window gesture in every grouping and density. Middle-click, like the menu's Open in background, opens the task in a new window behind this one without moving focus; Mod-click stays multi-select. A row on another server targets its own connection; offline rows never fall back to another server.
- Group labels use the same size and spacing in the task list and settings. Uppercase labels are reserved for data that is genuinely categorical, not routine navigation groups.
- Use spacing to separate adjacent navigation groups. Dividers are for real structural boundaries such as a persistent footer, not every list section.
- Compact actions use simple icons. A plus means add; richer folder imagery belongs in empty states or content where the object needs explanation.
- Settings navigation may have a different information structure, but should still use the shared sidebar item and group-label styles.

### Workbench Tabs

- Workbench tabs read as a quiet strip: an icon and muted label, with a soft filled pill for the active tab and no borders or separators. The active tab shows its close button; other tabs reveal it on hover or keyboard focus. Icons identify the surface and never turn into the close control.
- Each tab may add one toolbar row below the header, using the shared compact height. Segmented choices inside it use a borderless track with a raised active segment that slides between choices; they are toggle groups (`aria-pressed`), not tabs. The tab strip's active pill slides between tabs and a lighter pill follows the pointer or keyboard focus.
- "+" opens a New tab: a browser tab with nothing loaded. Its toolbar centres "Search or enter a URL". Below, Tools is a two-column tile grid (Changes, Terminal, Files, Side chat, Context, Pull request when linked, More tools…) with effective shortcuts and one gliding hover highlight, navigable by arrow keys. Choosing a tool turns the tab into that surface in place, or focuses it where it's already open. Suggested lists frequent recent sites from the task browser and hides when empty. A pane with no tabs shows the same page. The chevron beside "+" keeps the full "Open workbench surface" menu.
- Each task keeps its own panes by default. With "Keep the side panel when switching tasks" on, the next task's right pane takes the previous one's open state and, when it showed Changes (same mode), Files or Context, that surface for the next task's checkout. Task-owned tabs never move between tasks; the pane falls back to the task's own tab or its New tab page.
- A side question whose answer or error arrives out of view (another tab active, the pane closed, another task) shows an info-coloured dot after its tab title, named "new answer" in the tab's accessible name, until the tab is shown. Stopping an answer yourself never marks it.
- Keys follow focus. With focus in the pane, including the address field and a loaded page, Mod+W closes the active workbench tab instead of the window, and the task-switch keys (Ctrl+Tab by default) cycle the pane's tabs when it has more than one. Terminals keep their own Ctrl+W and Ctrl+Tab.
- Changes and Turn changes show Previous/Next file and "N of M" in their toolbar; J/K move between files only while focus is in the review pane and not in a field, menu, or selection.
- The Changes tab keeps viewed marks like the pull request Code tab: a Viewed checkbox ends every file header, ticking folds the file, and the toolbar counts "3 of 8 viewed". Marks are per task, review mode and file, and remember the changed lines they were made on; a file whose change moves on unfolds and says "Changed since viewed".
- Diff views stay quiet about files people rarely review. One classifier (`lib/changed-file-kind.ts`) sorts each path into lockfile, generated, migration, test or regular. Lockfiles, generated files and migrations start collapsed (diff options: Collapse lockfiles and generated files, on by default), carry a neutral label, dim in the Changes tree, list last in the changed-files card, and count apart from the main totals ("+ 1 lockfile"); tests only get a label. A file the reader opens stays open for that view, and Find in diff opens a folded file that holds a match.
- Changes, Turn changes and file diff tabs keep an 8px change rail along the diff scroller's right edge, hidden when everything fits: added, removed and changed blocks in muted success, destructive and neutral tones, Find matches in the warning tone while Find is open, and a box for the visible window. Pressing or dragging scrolls there (centred, instant); hovering a mark names its file and line. Marks come from hunk metadata mapped onto the virtualized item layout, never from measuring lines, and scrolling only moves the window box. The rail is hidden from assistive technology; the scroller stays the keyboard surface.
- Diff tabs keep layout, inline highlighting, whitespace, and find choices in one compact options menu in the toolbar row; the trigger icon shows the layout in effect. Find in diff floats at the top-right of the diff area like Find in task. Mod+F in a diff always opens it, never the diff library's own search panel, which stays on Mod+Alt+F (match case, whole word, regex).
- File tabs use the same find bar (Find in file) at the top-right of the file's content. Mod+F follows focus: the source view and rendered previews (Markdown, notebooks, documents, tables) are searchable; images, PDFs and media open the bar with a line saying find is not available there. Switching between Preview and Source closes it.
- In Working mode the Changes tab ends with a quiet commit panel: a branch line (name, ahead/behind, staged count, Stage all, Unstage all, and Push or Publish branch), a message field (Mod+Enter commits), then Generate message and Commit. Results and errors appear inline, with tool output collapsed. Stage checkboxes are always visible at the start of each file header so hovering never shifts rows. Remote connections show a single line instead.

- The task header's ship button names the one next step for its checkout: Commit, Commit & push, Push, Push & create PR, Create PR or View PR, and is absent when there is nothing to ship. A commit shows its generated message for editing first (Enter accepts); the run lists its stages by name, a failure names its stage and keeps what already succeeded, and on the default branch it offers a feature branch before committing. It refuses rather than resolves: behind, diverged, detached HEAD and conflicts disable it with the reason in its tooltip and accessible name. It never pushes without a press. A run that opens or finds a PR ends with a Watch PR stage, ticked by default and remembered (the same choice as Create pull request's "Watch pull request" checkbox); a failed watch keeps the PR. View PR on an open, unwatched PR gets a quiet Watch button beside it.
- An open PR states one readiness verdict (`shared/pull-request-readiness.ts`) wherever it appears in full: "Ready to merge" with a check in the success colour, else a muted "Still needed: …" list, or what the host can't report. The PR control, the Pull requests detail header and the row mark's tooltip use the same words. Palot shows readiness; the person merges, and a watch tells the agent so.
- A linked PR offers Fix review comments, Fix failing checks and Resolve conflicts only when there is something to fix. Each puts one removable chip into the owning task's composer; a sent chip stays compact in the transcript and opens the exact text the agent received.

### Composer

- Everything around the composer has one of four places. Tabs on the card's top edge hold standing context (Goal, Plan with its current step, Voice, Undo staged, running work). The request panel above the text field holds decisions (permissions, questions, forms, guest messages). One notice line above the card holds conditions (workspace missing, connection lost, usage limit, compact before sending), one at a time by priority with "+N" for the rest. The card itself holds the message being written: attachment and comment chips, upload progress, the queue and one error line. Nothing else stacks above the card.
- The Goal panel's Edit turns the objective into a text field in place (Mod+Enter saves, Escape cancels). OpenCode cannot change a goal's objective, so saving sets the goal again with `/goal <objective>`: the field says it restarts from round 1 and starts working, and refuses the control words pause, resume and clear. A met goal offers only Dismiss.
- One panel slot grows from the card's top edge and shows one thing: the launcher while it is open, else a pending request, else the open tab's panel. A request hidden by the launcher returns when it closes; tabs stay visible but inactive while a request is open. One tab panel is open at a time, per task.
- At rest the card has six controls: `+` and the agent pill on the left; one "model · effort" pill, the context pie (percentage from 70%, warning colour from 90%), the microphone and one primary button on the right. The row never wraps: labels drop first, then the pie and microphone fold into a `…` menu; tabs fold into "+N". The primary is the default delivery (Send, Queue or Steer), Run, Compact and send, Stop, or a request's main action; holding Mod previews the other delivery and Mod+Enter sends it. Stop sits beside it while the agent works and there is a draft. No split button, no chevron.
- The launcher (`+`, Mod+/ in the composer, typed `/` at the start of the draft, `@`, `$`) holds only things you put into the message: files, recent outputs, stashed prompts, commands, skills, mentions and a shell command. The one exception is Approvals, its last entry: a setting of the task the message goes to. Navigation belongs to the command palette, the rail and the task header, never the launcher. One list and one keyboard model serve every entry point, and its data loads before first use.
- Picking `/review` (typed, or under Commands) opens a Review level in the launcher instead of a chip: Uncommitted changes, Against the base branch (the Changes tab's review base, disabled when there is none), A commit…, saved instructions marked Saved, and Custom instructions…. A target or saved entry runs `/review <text>` in the task at once through the normal send path and leaves the draft alone; the two "…" rows put `/review ` in the draft for a hash or one-off text. Saved instructions live under Settings → General → Review instructions (add, edit, remove; names are unique).
- Requests never answer by accident. A request takes no click or key for 500 ms after it comes into view; one that arrives while the person types (or within 1.5 s of a keystroke) waits for a pause before Enter answers it; Escape leaves it for the text field and never approves or denies. Only a field that was empty when the request arrived doubles as its feedback or answer; a draft that existed before it never becomes feedback, and the panel brings its own feedback input instead.
- Approvals show as a warning chip after the agent pill only when they are not Defaults. They change in the launcher's Approvals entry, which shows the current mode (Defaults, Full access, Custom) and drills into the presets; while the mode is Custom it says that custom session rules are active and a preset replaces them. The chip opens the launcher on that entry. Moving the highlight never arms Full access; picking it asks first, and Defaults applies at once.
- The notice line is `ComposerNotice`, an exception to the one-notice-component rule: the composer gives conditions a single line above the card, shown one at a time by priority with "+N", in place of the separate strips that used to stack there, and `Banner`'s title, body and actions do not fit that line. It keeps Banner's tone wash and stays mounted so it can animate out.
- A subagent task has the same composer as any task, so you can steer it or ask it something. Its context bar says "Messages go to this subagent; it reports back to the main task" instead of the checkout and branch (the parent's); a bar above the composer steps between sibling subagents, and the header breadcrumb leads back to the parent.

### Shared Controls

- The composer's model and reasoning effort share one pill. The pill shows the maker's icon (from the brand, else the provider's icon, else none) and a short model name without a leading brand ("Opus 5.5") when the rest still names the model and no other listed model shortens to the same; its accessible name, tooltip and everything else keep the full name, and the popover's list keeps provider icons. Its popover lists models with the highlighted model's efforts beside them and actions in its footer: Manage models, and Send to several models for a new task. Shift+Mod+D cycles Auto → each effort → Auto. Toolbar labels and icons use the shared compact composer button sizing.
- Composer and new-task choices share one picker (`ComposerPicker`, on the fluid Combobox): optional punctuation-insensitive search, labelled sections, rich rows (description, badges, metadata, a check on the current row, disabled rows that say why), an optional detail pane when the popup has room, and footer actions. The model picker lists Favorites and Recent (last five per project) above every visible model grouped by provider; those sections step aside while searching, and models released in the last 30 days show New. A paid model OpenCode Console limits shows what is left in place of its context size ("62% left · resets 18:00"), in the warning colour under 15% and destructive once reached; the selected model warns once per limit window when low and when reached. A choice closes the popup only after it succeeds, returns focus to the composer, and reports failures in one toast.
- Approval presets reflect authoritative session rules: Defaults clears session overrides; Full access is an explicitly confirmed wildcard allow. Other rules display Custom. New independent drafts never inherit a locally remembered Full access choice, and pending requests are never silently answered by the selector.
- Markdown renders GitHub's raw HTML subset with the chat typesetting. Only allowlisted lowercase tags become elements; component names, generics and other tags (`<Button>`, `Array<string>`, `<script>`) stay readable as literal text. `<details>` uses the same bordered disclosure as other collapsible Markdown (chevron and summary row), `<kbd>` is a small keycap, `<mark>` a warning tint, tables share the Markdown table frame, `align` becomes text alignment (or a float for images), and `<picture>` light/dark sources follow Palot's resolved color scheme rather than the OS.
- Agent artifacts (OpenCode's opt-in `experimental.artifacts`) replace their tool row with one compact bordered card per call: a kind icon, the title, "Published · HTML · updated 3m ago", and Open, which shows the artifact in the task's Palot Browser and reuses its tab. Cards follow later updates through the project's artifact list, and published cards stay visible when their activity folds.
- Questions, forms, and permissions from descendant sessions surface in the parent request area with the originating sub-agent identified. Replies and dismissals retain the original session and request ownership. Needs input takes priority over Working; summary cards use request/lifecycle events, not transcript previews, to show that state.

- Confirming a start, restart or replacement of the shared local OpenCode service names what it would stop: a warning Banner says "3 tasks are working; restarting stops them", lists up to five working root tasks on local profiles (as the task list counts them) with "and N more", and the confirm button reads "Restart anyway". It reads the task list when the dialog opens and adds nothing when no task is working.
- Composer connection context belongs beside the project/branch controls, not in a separate input row. Hide connected local destinations; show a compact green-cloud badge for remote destinations and an explicit warning when the execution connection is offline.

- Prefer the local shadcn/ui primitives and improve the primitive when several callers need the same behavior.
- Popup lists (menus, selects, comboboxes) draw one gliding highlight behind their rows instead of per-row fills; pointer and keyboard always light the same row. Popups and tooltips enter on a short spring and exit faster; under reduced motion they only fade. Motion timings come from the three shared spring tiers (`lib/springs.ts`), never ad-hoc durations.
- The global command palette opens with a fixed top edge and a capped height; results filter beneath a stationary search field. All · Tasks · Files · Commands · Settings tabs sit under the field (Files lists the open task's files; All adds up to five file matches after tasks and commands once something is typed); ←/→ switch tabs only when the field is empty or the caret is at the edge it points past. The footer shows at most four hints, naming Enter after the highlighted row's action. Typing in All or Tasks adds a Messages group that searches loaded transcripts and, on request, the latest messages of up to 30 recent tasks per server; its heading states that coverage and never implies full history.
- Selecting text inside one assistant reply offers Ask about selection, which opens a tool-free side question with the exact quote and a link back to the reply. Side questions keep their questions and answers and accept follow-ups.
- The composer's text field shows mentions, skills, terminal quotes, PR links and review comments as inline chips: one caret step, one Backspace, an accessible name. `@` lists the active workbench file and other open files first, each file with its workspace folder cut from the start. A recent output's chip offers Open original task in its menu (right-click, the context-menu key or Shift+F10 on the selected chip); the launcher never lists that navigation.
- Composer suggestions label their groups (References, Agents, Files) only when a query mixes kinds; single-kind lists stay unlabelled.
- A transcript turn runs from a prompt until OpenCode's idle marker, or until new input arrives after the agent had answered. It holds every step, notices, and prompts steered in meanwhile; steers show inline with a muted "Steer" label and stay visible when the turn's work folds. The answer is the last text after the turn's last tool call and steer (the provider's phase wins when it gives one); earlier text is commentary and folds with the work.
- Review and browser element comments in a sent message show as quote chips under its text, never as the sentences the agent received: an icon, `path:L12–18` in code type (or the element's label), a destructive "removed" tag for lines numbered in the old version, and the comment clamped to four lines. Pressing a chip opens the file at those lines, the file's diff for removed lines, or the commented page. Stored message metadata wins; the sentence format Palot writes is parsed only without it.
- A prompt an automation sent (OpenCode's `metadata.automation` or Palot's own scheduler) shows a muted "Automation · <name>" line with a clock above its bubble, "· ran late" when late, after a "Steer ·" label when steered; it links to Scheduled. It keeps Copy prompt but not Edit from here, stays out of Up-arrow history, and reads as "Automation" in the outline and message search.
- Sending a message follows the transcript's bottom only when the reader was already there. A reader who scrolled up keeps their place, and Scroll to bottom stays until they use it.
- A running turn shows one clock in its turn bar ("Working for 42s"). Once it ends, the bar is the fold toggle and reads "Worked for {d}" followed by what the work did ("changed 3 files +40 −12 · ran 4 commands · 1 failed"), "You stopped after {d}" or "Failed after {d}". Only the failed clause uses the destructive colour. While subagents the task started still run, its latest settled turn reads "Waiting for N subagents" instead; the task finishes, and notifies, once they and the runs their reports wake are done. A subagent row follows its child task's state, and its latest report is its result; an idle subagent whose own subagents or background work still run reads "Waiting for subagent" or "Waiting for background work", never Finished. One live line under the running turn says what the task is doing or waiting on (approval, your answer, Stopping, retry, compaction, subagents, a command with Move to background after 5 s, tools, the latest thought, or Working); it has no clock, and its waiting states are buttons that focus the request.
- Inside an opened turn, a group header appears only when it saves space: a settled turn with one activity group, and any group of three rows or fewer, shows its rows directly; larger groups in a multi-group turn keep a collapsed header. Running turns keep the live group header. Without a header, failures show on the row's Failed badge and the turn bar's failed clause.
- Every finished turn that changed files ends with a changed-files card (under its answer, or under its work when there is none). The latest settled turn's card adds Ask for review and a dismiss button that removes only those follow-ups. Cards never appear while the turn is working.
- Activity group titles put changes and commands before reading, name up to three changed files, show at most three clauses ("and N other actions"), and add a destructive " · N failed" suffix; stopped calls are not failures. Failed tool rows say what was attempted ("Tried to read app.ts"). Notices from OpenCode (goal, restart, instructions, image and video jobs, console watches) are one-line rows with their own icon; a finished video expands to play it when the task's workspace can read the file; background reports that arrive after their launching turn merge by kind and outcome into one expandable row ("Finished 2 subagents"; a report sent while the subagent's own work still ran reads "1 subagent waiting for its subagent"). Durations use one format (`42s`, `1m 5s`, `250ms`, `1.4s`). Delegated subagents use one compact row: agent, description, elapsed time, and Stop while running.
- A Code Mode script (`execute`, as with OpenCode's `full_codemode`) is not a card of its own: each call it made is the row the same call would get if the agent had made it directly (commands, "Read 3 files", edits, web searches, image reads), grouped, titled and counted with the turn's other work, and live while the script runs. The script itself stays one hover action away: a `{}` button on its calls' rows opens its source and result under the row. OpenCode records no output or exit code per call, so a script's command expands to say so with a link to the script's result. From OpenCode 2.4 a script lists the files it changed with their diffs, live while it runs: each edit, write or patch row shows its own change, and a change no call made (`Bun.write`) gets an "Updated <file>" row after the calls. A change listed with counts only (past OpenCode's 50-file or 200 KB cap), a background script, and older servers show the turn's diff for the file instead (once, on the file's last change in the turn), or no counts when there is none. The script keeps a row of its own only to say how it ended when that matters: "Script failed: …" after its calls when it threw (one failure, unless a failed call already shows where), "Moved script to background" and later "Ran script in background", or "Ran a script" when it called nothing Palot recognises. Calls a script made before it moved to the background stay as rows while the task stays loaded; OpenCode drops them.
- A command cancelled through the shell ("Command cancelled") is stopped like an interrupted call, never failed. A call stopped before any of its input was written did nothing and has no row.
- Shortcut labels, tooltips, menu hints, and `aria-keyshortcuts` always show the effective binding through `useShortcutKeys`/`shortcutKeys`; never hard-code key names. Built-in composer and system keys are locked and show a lock with the reason.
- Notification sounds are short, quiet cues synthesized at runtime. Every event offers Off and a preview, and only one window plays a given event.
- A single choice among a few visible options uses `ChoiceGroup` (radio semantics, one roving tab stop), never toggle buttons with `aria-pressed`; its `card` variant suits options with an icon and description. Toggle groups remain for toolbar segments. Independent multi-select uses `CheckList`, keyed by value.
- Values people copy (ids, paths, URLs, tokens) use `CopyField`; secrets start concealed.
- Palot has one notice component, `Banner` (`SettingsNotice` in settings); the composer's notice line is the one exception (see Composer). `Alert` is legacy and is migrated when touched. Keep a banner mounted and toggle `open` so it can animate out.
- Advanced or rarely changed settings sit in a `SettingsDisclosure`, closed by default. Settings rows use two paddings, `default` and `compact` (long uniform lists); never hand-pad a row.
- "Switching from another agent?" is a prompt, not an importer. Settings → General (Getting started) opens a small dialog, and the welcome guide shows the same picker as an optional last step with Skip and start working: one `ChoiceGroup` card tile per agent (Claude Code, Codex, T3 Code, Pi, Cursor, OpenCode app, Other), a Run in select (No project by default, or a project), a collapsed Show prompt, Copy prompt and Start. Start creates the task like a new task in that checkout (or a project-free chat), titles it "Switch from <agent>" and sends the prompt from `lib/switching-prompt.ts`. Palot detects, counts and changes nothing itself; the prompt has the agent survey, propose, wait for an OK, back up and report how to undo.
- Settings → Machines (OpenCode's experimental machines) has one section per connected server that has them on, named for the server, with Add machine in its header; servers without the flag show nothing, and the page explains the flag when none has it. Rows show the machine's name, a Connected/Offline/Waiting to join badge, and system and link while connected; Remove is the in-place armed confirm. Add machine is a dialog that names the machine, then shows the concealed join string (`CopyField`), its expiry and addresses, and a live "Waiting for … to connect" line that flips to connected.
- A path on another OpenCode machine (`devbox:/…`, OpenCode's machine path syntax; `local:` means the server, Windows drives and URLs never count) is one parser (`shared/machine-path.ts`). Wherever such a path shows, a small `MachineBadge` names the machine (file links, tool rows), the turn bar adds "on devbox", and a folded activity group adds "· on devbox". It never resolves locally: no file tab, editor, reveal, Palot Browser or `file://` href; opening it says where it is and offers Copy path, because OpenCode's file API reads only its own server's files.
- Settings pages are one centred column, at most 720px wide (Diagnostics keeps room for its charts). Each page is groups of `SettingsRow`s in a `SettingsGroup` card under a `SettingsSection` label: a short sentence-case label in the shared group-label size, separated from the next group by spacing, never a divider. A row puts its title and description on the left and a small control (switch, select, short input) on the right (`layout="inline"`); a wide control (text area, list, table, editor, long path or command) goes under its label at full width (`layout="stacked"`). Below the `@lg` settings container (about 520px) inline rows stack too. A row whose value has one default passes `reset` (from `useSetting` or `settingReset`, reading the default its atom declares): a small Reset to default icon button with a tooltip appears just before the right-aligned control (at the end of the title line for stacked rows) while the value differs, so the control and the column's right edge never move, and focus returns to the control after a reset. Values without one default (per server, per project, lists) get no reset.
- Dialogs enter on `spring.slow` and exit on its quicker tween; under reduced motion they only fade. The app honors Palot's own Reduce Motion setting through one `MotionConfig`.
- A task's `/goal` is the composer's Goal tab: "Goal · round N of M", "Goal · paused" in the warning tone, or "Goal met" briefly before the tab leaves. Its panel shows the objective, Pause/Resume and Clear (Dismiss once met), the reviewer's latest reason, and rounds. OpenCode's continuation prompts stay out of the transcript; its "Goal: …" notice marks the start.
- Undelivered messages sit in queue rows inside the composer card, mirrored from OpenCode's session inbox: a one-line preview, attachment count, and a Queued/Steering/Sending/Failed state, with Steer now, Edit, Delete (Undo returns it to the composer), and Retry. More than two collapse to a count. When the task is idle with messages still waiting, the queue shows "Queue paused…" with Resume (sends the next, then OpenCode continues) and Clear (confirm in place). Stop does not resume parked steers.
- Alt+Enter while the agent works queues the message first; queued rows after the first show Move to top on hover or focus. OpenCode's inbox cannot reorder, so a move re-admits the other queued messages behind it and withdraws the originals only once every copy is in; rows keep their place and key meanwhile, and a failure leaves the queue as it was. Steers and a message being edited are never moved.
- The composer context meter is a pie before the microphone: its percentage shows from 70% and it takes the warning colour from 90%. Hover or press opens a popover with "Context window: N% used (M% left)" or "N% full", used / window tokens, a cached / uncached / output bar, session cost, total processed, last compaction, Compact now (disabled with its reason), and Context details. When a task with at least 100k tokens of context has been idle for an hour, the notice line suggests compacting first: Compact first / Send as is drives the primary (Compact and send), with Don't suggest again in its menu; both are General settings. The Context tab reads top to bottom: Window, What the model sees (readable rows, View raw), Instructions & rules (confirm-in-place removal), Compaction history (before → after, Jump to), with collapsed Session totals. Developer diagnostics appear only with Palot diagnostics on.
- F6 and Shift+F6 move focus between the areas marked `data-focus-region` (task list, transcript, composer, open workbench panes), returning to the element last focused in each. Every such area has an accessible name. They do nothing while a modal is open.
- Task menus offer Mark as unread or Mark as read. A task marked unread shows its unread dot even on the selected row and has no "New" divider; opening it again clears the mark. The mark is local to Palot (OpenCode has no unread API).
- Reduced motion removes movement and size changes but keeps colour and opacity transitions. Progress indicators (spinners, pulses, the thinking dot) keep running. Streamed text appears without the word fade. The OS media query and the `data-reduced-motion` attribute behave identically; in JS read them through `prefersReducedMotion()` / `useReducedMotion()`, never `matchMedia`.
- Shell panes (navigation, right, bottom) animate independently. A toggle that interrupts a pane's animation continues from its current position. Open uses `spring.moderate`, close its exit tween.
- Transitions name the properties that change; avoid `transition-all`. Never transition padding or other layout properties on hover. Filled buttons (default, destructive) have a pressed state one step stronger than hover.
- Request cards (permissions, questions, forms) enter with a short fade and rise on `spring.moderate` and leave with its opacity-only exit; their area keeps its height until the fade ends, then closes without animating height. A leaving card takes no input, is hidden from assistive technology and hands focus to the composer's message box.
- Messages queued behind a running turn read as queued with Steer now; only an idle task shows Queue paused. With an empty composer, Mod+Enter steers the first queued message, and that row's Steer now tooltip names the shortcut. Task menus offer Copy task ID beside the other copy actions. Keys held by a locked shortcut cannot be assigned elsewhere; Settings explains why instead of offering Replace.
- Mid-task switches show as neutral boundary rows where they happened: "Switched to <model> · <effort>", "Switched reasoning effort to <effort>", or "Switched to <Agent> agent". Switches before the first prompt, switches back to what was in effect, and all but the last switch between two messages stay hidden.
- A provider limit is named by its kind everywhere it shows (turn row, notice line, task list, notification), with its reset when known, from one reader (`shared/provider-limit.ts`). The failed turn offers Switch model, the page that raises the limit when the error names one, and Copy request for admin when only a workspace admin can.
- A tool row whose call waits on a permission request shows a warning **Needs approval** badge instead of its running timer. The badge is a button beside the row's disclosure; it moves focus to the request. Rows expose `data-palot-awaiting-approval`.
- Compaction rows read "Compacting context" (adding "This can take a few minutes" after 10 s), then "Context automatically compacted" or "Context compacted"; the detail shows context before → after. Only the newest failed compaction offers Retry, and only while the task is idle. Rows expose `data-palot-compaction="<message ID>"`; other surfaces jump to them through `transcriptJumpTargetAtom`. Subagent tasks show "Parent › Agent · description" in the header; the parent crumb navigates up. When the agent keeps a plan, the composer's Plan tab reads "Plan · n/m" with the current step, then "Plan · done" briefly before it leaves.
- The Scheduled page shows OpenCode's own automations in a second section, "OpenCode automations", below Palot's scheduled tasks and under the same search and status filter. Rows are read-only apart from Pause/Resume and Delete (confirmed in place), name the server only when several have rows, and link the task they prompt and the task that created them. A quiet line says they run inside OpenCode even when Palot is closed. The section is absent when no connected server reports any.
- The Usage page loads its summary at once and everything heavier on demand: tool details when shown, tasks and automations when scrolled near, a project when opened. Figures OpenCode reports differently from the summary say so in place: task costs are lifetime totals of tasks active in the range, model rows leave out compaction, and a quiet line under the reported cost names what it leaves out. Terms that need a definition (cache hit rate, cost per 1M tokens, Code Mode share) carry it in a tooltip on a dotted-underlined label.
- Project settings list Scripts: name, the exact command in a `CopyField`, trigger, and timeout. Only local connections run them, through the user's shell in the task's directory; other connections say why. Results arrive as one quiet toast with View output and are never sent to the agent.
- Component variants own typography and visual states. Call-site classes should mainly describe layout or a genuinely unique product state.
- Focus, hover, selected, disabled, loading, empty, and error states use the same semantic treatment wherever the interaction is equivalent.
- Controls use plain labels that describe what changes. Avoid exposing internal implementation terms when a user-facing material, pane, or task concept is available.

### Providers and Models settings

- Providers: connected providers are cards with icon, name, a source badge (Account, API key, External, Env, Config, Integration), a "N of M models shown" link to that provider on Models, and Disconnect, which confirms in place and says which environment or config source remains. A provider turned off by a config `provider.use` deny policy keeps its card with a "Disabled by config" notice naming the policy and file. Add a provider lists popular providers, with Browse all and search for the rest; environment-only providers show their variable names as copy fields. Integration sources sit in a collapsed Advanced disclosure. A connection OpenCode reports as needing sign-in shows Needs sign-in on its card with OpenCode's message and one fix: the provider's sign-in link, Reconnect, or, for Claude Agent, its setup. Claude Agent connects through a guided setup instead of the credential form: numbered steps to install Claude Code and run `claude auth login` (copy fields, never run for the user), then Check connection, which OpenCode answers with Not found, Not signed in, or ready. A failed reply that names a Claude Code command offers the setup and a copy of that command.
- Models: Defaults come first (OpenCode's configured default with its config file, then Palot's per-project override and effort, then read-only agent models). Models are grouped by provider in collapsible groups with "N of M shown" and a show-all switch; search and filter chips (Shown, Hidden, New, Tools, Vision, Reasoning, Deprecated) keep the groups. Rows show status/New badges, context/output, base price per million tokens (Free at zero, tier note), effort levels, and release date. Picker order is set within a provider by drag or Move to top; `?provider=` expands and scrolls to one provider.

### Connections and pairing

- Pairing is two step-by-step dialogs with one main action per step: Share this computer (create a code, name it, scan or paste) and Connect to another computer (get a code, paste it, name it and connect). A pairing code is a secret: it is never printed, only placed in the QR or the clipboard, masked once pasted, and never logged or echoed in an error.
- Codes carry the sharing computer's name; a name typed on the connecting side wins, and codes without one fall back to the address. Pairing a server Palot already knows renews that connection instead of adding a duplicate.
- A failed connection names the step that failed (reaching the address, the tunnel or proxy, the certificate, the code, the saved sign-in, the OpenCode version) and gives the fix in plain words.
- Each server row shows its address, OpenCode version and why it is offline, with Reconnect, and keeps Rename, Test connection, Pair again, Edit and Remove in one menu. What OpenCode cannot do (signing out one device, knowing a code was used, turning on remote access without the CLI) is said plainly, never faked.

## Do's and Don'ts

- Do verify surfaces in light, dark, high-contrast, translucent, opaque, and Reduce Transparency modes.
- Do verify that changing interface size visibly affects a component without breaking its layout.
- Do reuse shared tokens and primitives for color, typography, dividers, radii, and opacity.
- Do match equivalent navigation and control patterns elsewhere in Palot.
- Do test reusable panes at their minimum supported width and height.
- Do preserve keyboard focus, readable contrast, and clear selected states.
- Don't add local styling that duplicates a shared token or component variant.
- Don't use viewport assumptions inside a component that should respond to its allocated pane.
